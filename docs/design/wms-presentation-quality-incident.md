# WMS Presentation Artifact Quality Incident

**Date:** 2026-08-03  
**Product:** WePrompt  
**Model used:** Kimi  
**Artifact reviewed:** `WMS_SRS_Presentation.pptx`  
**Source referenced by the user:** `WMS_SRS.docx`

## Executive summary

A user asked WePrompt, using the Kimi model, to create a PowerPoint presentation from a Word-based WMS software requirements specification. WePrompt produced and confidently delivered an 11-slide `.pptx`, but the artifact was not acceptable as a professional presentation.

The file is technically valid and opens successfully, but it fails in three more important dimensions:

1. **Source fidelity:** Kimi reported that it could not extract the Word document and then continued with generic WMS content instead of stopping or using another extraction method.
2. **Presentation design:** The deck is almost entirely unformatted text, with no meaningful visual composition, diagrams, tables, charts, images, or speaker notes.
3. **Quality assurance:** The deck was delivered without a rendered-slide review. Existing OfficeCLI structural checks returned success even though the visible result was clearly defective.

This should be treated as a WePrompt artifact-workflow failure rather than only a weak model response. The product allowed the model to continue after losing its source, use a minimal rendering path, and interpret structural validity as delivery readiness.

## What the user received

The generated deck contains 11 slides covering topics such as objectives, functional requirements, non-functional requirements, database design, APIs, roles, workflows, and error codes.

Inspection of the actual PPTX found:

- The file was generated by **OfficeCLI 1.0.143**.
- Every slide contains only two text shapes: a title and a body text box.
- The deck contains **zero images or other media**.
- The deck contains **zero speaker-note slides**.
- Slides 2–11 contain literal `\n` text instead of real paragraph or bullet breaks.
- The same basic text-only composition is repeated throughout the deck.
- Content that should be represented visually is flattened into paragraphs:
  - functional modules are one dense text block;
  - database entities are one dense text block;
  - API endpoints are one dense text block;
  - inbound and outbound workflows are one dense text block.
- There is no coherent theme, palette, brand treatment, typographic hierarchy, section rhythm, or designed closing.

The result behaves more like a Word outline pasted onto blank slides than a presentation designed for an audience.

## Kimi's self-analysis

After the user challenged the result, Kimi produced a detailed self-audit. Most of that audit is consistent with the artifact.

Kimi stated that it:

- could not extract the attached `.docx` through its initial read path;
- confused loading OfficeCLI instructions with actually running OfficeCLI;
- initially encountered an unavailable OfficeCLI command;
- received empty or insufficient output from the OfficeCLI Word inspection commands it tried;
- did not exhaust other extraction methods such as deeper OfficeCLI inspection, OOXML extraction, or a DOCX parser;
- used generic WMS knowledge to fill the slides after source extraction failed;
- used a basic title-plus-text layout for almost every slide;
- placed whole sections into single text shapes instead of proper paragraphs, bullets, tables, or diagrams;
- did not apply a master, theme, consistent palette, or visual hierarchy;
- did not use tables, charts, connectors, pictures, or other informative visuals;
- did not render or preview the slides before delivery.

That self-analysis is useful evidence, but it came too late. The model could identify the required quality standards after delivery even though the execution path did not enforce them before delivery.

Some items in Kimi's audit are secondary rather than root causes:

- Ordinary shapes are not inherently inferior to placeholders.
- A blank slide layout can support a high-quality custom design.
- Requiring outline confirmation is a product and UX decision, not a universal quality requirement.
- The absence of a rollback plan did not cause the initial artifact failure.

The decisive failures were loss of source grounding, continuation with invented content, lack of an appropriate slide-composition system, and absence of rendered visual QA.

## Reconstructed failure chain

```text
User attaches WMS_SRS.docx and requests a presentation
    ↓
Initial DOCX extraction returns no usable content
    ↓
The model stops troubleshooting the source too early
    ↓
The model continues using generic WMS assumptions
    ↓
OfficeCLI creates a structurally valid but minimal deck
    ↓
All content is flattened into title + body text shapes
    ↓
OfficeCLI validation reports success
    ↓
No rendered-slide visual audit or repair cycle occurs
    ↓
WePrompt presents the artifact as complete
```

## Why the existing checks did not protect the user

The reviewed file passes both of these commands:

```text
officecli validate WMS_SRS_Presentation.pptx
→ Validation passed: no errors found.

officecli view WMS_SRS_Presentation.pptx issues
→ Found 0 issue(s).
```

Those results show that the current checks validate package and geometry conditions, not whether the deck is grounded, readable, visually composed, or suitable for delivery. They also fail to flag the literal `\n` sequences visible throughout the deck.

WePrompt already contains stronger presentation guidance in two places:

- `skills/presentation-maker/` defines source extraction, outline planning, theme commitment, designed slide types, and a validation loop.
- The Template Gallery PPTX path tells the model to load the OfficeCLI PPTX skill, extract real source content, use visuals and notes, render every slide, inspect the images, and repair defects before delivery.

However, the standalone presentation-maker skill is documented as something that must be packaged, imported, and enabled by the user. The Template Gallery protections apply to template-driven sends. A normal conversation request is therefore not guaranteed to receive either enforced presentation-quality contract, even when generic OfficeCLI capability is available.

## Root-cause assessment

### Primary product causes

1. **No fail-closed source-grounding gate**

   WePrompt allowed artifact generation to continue after the attached source could not be read.

2. **Presentation workflow is not guaranteed**

   Strong presentation instructions exist, but they are not necessarily applied to every request that intends to create a `.pptx`.

3. **Structural validation is treated as sufficient evidence**

   A valid OpenXML package is not the same as a delivery-ready presentation.

4. **Rendered-output QA is optional in practice**

   Nothing prevented delivery when no slide screenshots had been inspected.

5. **No automated artifact-quality policy**

   The pipeline did not reject obvious anti-patterns such as literal escape sequences, text-only repetition, missing notes, missing visual anchors, and excessive text density.

### Model contribution

Kimi made poor execution decisions: it stopped troubleshooting too early, invented content, chose the easiest rendering structure, and skipped visual inspection. However, this failure mode is model-agnostic: any model can reproduce it on the same ungated path. Relying on the model to remember every quality step is fragile. The product should make these steps explicit, observable, and blocking.

### Tool contribution

OfficeCLI successfully created a valid file, but its current validation and issue-detection output did not identify the visible quality problems. This is a limitation of the existing automated checks, not evidence that OfficeCLI alone caused the deck's design decisions.

## Recommended product response

### Priority 1 — Protect source fidelity

- Treat empty or failed source extraction as a blocking state.
- Attempt defined fallback extractors in order.
- If extraction still fails, ask the user for another format or clarification.
- Never create factual slides from model assumptions when a source document was supplied.
- Produce a source-facts record and require slide claims to trace back to it.

### Priority 2 — Guarantee presentation routing

- Detect presentation intent and automatically invoke one canonical PPTX workflow.
- Do not require users to know about a slash command, custom assistant, manually enabled skill, or Template Gallery path to receive baseline presentation quality.
- Verify required tools before beginning artifact construction.
- Preserve the existing reference-deck rule when a template is selected; for a no-template request, use the canonical OfficeCLI visual system instead of applying the template-only "never build from scratch" instruction literally.

### Priority 3 — Add a deterministic delivery-readiness gate

In addition to structural validation, reject a deck mechanically when any of the following is true:

- literal `\n` or other escaped formatting is visible;
- source extraction is required but unverified;
- unresolved placeholder text remains;
- the exact final artifact version has not been rendered successfully;
- required gate evidence is absent or belongs to a different artifact hash.

Treat speaker notes and non-text visuals as workflow-policy checks rather than universal file-validity rules. For example, a selected presentation workflow may require notes on every content slide, while covers, dividers, quote slides, and explicitly minimalist slides can be valid exceptions. A deck in which all content slides are text-only is a strong deterministic defect signal; a single text-only slide is not automatically defective.

### Priority 4 — Require rendered visual QA and repair

Use the following artifact flow:

```text
Source extraction
→ grounded artifact brief
→ slide narrative and layout plan
→ deterministic rendering
→ render every slide to an image
→ defect report with named problems
→ targeted repair
→ repeat until clean or stop after a bounded number of attempts
→ delivery
```

The rendered audit should make the judgment-based decisions that do not belong in the mechanical gate: typography hierarchy, layout capacity, spacing, density, contrast, repeated compositions, visual-to-content fit, whether structured material was flattened into prose without justification, missing metadata, and narrative flow. It should produce named defects and run a bounded repair loop rather than returning a vague "make it better" instruction.

### Priority 5 — Make quality evidence visible

The completion message should distinguish:

- source successfully extracted;
- artifact successfully generated;
- structural validation passed;
- all slides rendered;
- visual QA passed;
- any unresolved limitations.

The product should not summarize all of these states as simply "file created successfully."

## Suggested issue statement

> When a user asks WePrompt to create a PPTX from an attached source document, the system may continue after source extraction fails, generate ungrounded text-only slides, and deliver the artifact after structural validation without rendered visual QA. The result can be technically valid but factually unreliable and visibly below presentation quality standards.

## Proposed acceptance criteria

- A failed or empty source extraction cannot silently proceed to artifact generation.
- Every source-based deck records successful source extraction before build starts.
- Every PPTX request receives the canonical presentation-generation workflow.
- Literal escape sequences such as `\n` are detected before delivery.
- Every slide is rendered and reviewed before completion is reported.
- The QA system produces named defects and supports a bounded repair loop.
- A deck matching the reviewed artifact's structure—11 repeated text-only slides, no notes, no visual anchors, and literal `\n` content—is rejected as not delivery-ready.

## Final assessment

This incident is not best described as "Kimi is bad at PowerPoint." Kimi's later self-analysis shows that the model can articulate many of the correct standards. The deeper issue is that WePrompt did not reliably turn those standards into an enforced artifact pipeline.

The product accepted this sequence:

```text
tool completed → file opens → delivery succeeds
```

It needs to enforce this sequence instead:

```text
source grounded → artifact planned → artifact rendered
→ output inspected → defects repaired → delivery succeeds
```

## Addendum — engineering triage (2026-08-03)

Verified against the repository at `origin/sprint1`. This addendum refines the
recommendations above; where they differ, the addendum is the adopted scope.

### Relationship to BUG-003 (stays closed)

BUG-003 (closed by MR !47) gates the _corruption_ class: malformed OOXML fails
`officecli validate` inside `OfficeArtifactService`, delivery fails closed, and
staged copies protect the last valid revision. The deck in this incident is
structurally valid, so that gate correctly passes it. This incident defines the
_adjacent_ class — grounding, composition, and rendered QA — and is a new epic,
not a regression or reopening of BUG-003.

### Corrected framing of the routing gap

A plain conversation request is **not guaranteed to receive either enforced
presentation-quality contract**. Generic OfficeCLI capability may still be
available — and evidently was used here. What is absent is the guaranteed
workflow: the stronger extraction/QA contract lives only in the template path
(`packages/desktop/src/renderer/components/chat/TemplateGallery/directive.ts:33`),
and the standalone skill is opt-in
(`skills/presentation-maker/README.md`, "Install into WePrompt": zip → Skills
Hub → Import).

### Deterministic gates vs. model-evaluated QA (revises Priority 3)

Safe **hard gates** (deterministic, cheap, block delivery):

- Source extraction succeeded and produced traceable content.
- No literal escape sequences (`\n`) or unresolved placeholders.
- Every final slide was rendered from the exact final artifact version/hash.
- Structural validation passed.
- Required QA evidence exists.

Deterministic signals that are **conditional**, not unconditional failures:

- Missing speaker notes fails only when the selected workflow requires notes.
- Zero-visual slides need slide-type exemptions (covers, dividers, quotes,
  intentionally minimal slides). The safer condition is "all content slides
  are text-only" or "the deck violates its declared layout plan."

Judgment calls that belong in **model-evaluated rendered QA**, never in the
mechanical gate: typography quality, density vs. layout capacity, composition,
and whether prose should have become a table or diagram. Automating these as
hard gates produces false positives that block legitimate decks.

### Generalize the invariants, not the Template Gallery directive

"Never build a deck from scratch" is correct only when a reference deck is
attached. The canonical router must branch:

- **Template selected** → clone and preserve the reference deck.
- **No template selected** → use a bundled default visual system / layout
  library (this default composition path is required NEW work, not
  integration).
- **Both paths** → enforce grounding, planning, rendering, QA, repair, and
  honest completion states.

### Adopted Sprint 2 slicing

| Slice                        | Outcome                                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------------------------- |
| 2A — Immediate containment   | Block failed extraction, literal escapes, unresolved placeholders, and delivery without render evidence |
| 2B — Canonical orchestration | Route all PPTX intent through a shared artifact contract, with template and no-template branches        |
| 2C — Visual-quality loop     | Render audit, named defect report, bounded repair, latency/cost controls                                |
| 2D — Completion semantics    | Show generated, grounded, validated, rendered, reviewed, and delivery-ready as distinct states          |

2A ships first to protect users while 2C is designed properly. The incident is
model-agnostic — Kimi is the reproducer, not the issue definition. Backlog:
one artifact-quality epic with separately deliverable issues per slice.
